[verifier](../../tools/windows_preflight_archive.py). Select a stable,


Native Windows PowerShell, using the existing trusted environment:

```powershell

    --archive 'C:\Users\DEVELOPER\AppData\Local\FIRMAVEX-Preflight-Batch35-EXISTING'

```

Replace the example directory with an explicitly selected existing archive. The
verifier requires no runtime tools, network access, installer, signer or firmware.
It writes deterministic sanitized JSON to standard output and a short summary to
standard error. It creates no output files and never extracts, executes, repairs,
reseals or deletes archive members. To retain the report, explicitly redirect it
to a fresh location **outside** the selected archive; do not overwrite original
evidence. Preserve every failed or partial archive unchanged.

The command is a read-only assessment, not the native Batch 35 operator workflow.
Running this verifier on Linux does not run or reproduce Windows validation.

## Accepted archive structure

The supported layout is derived from `Archive.seal()`, `run_operator()` and
`_synthetic_assessments()` in the
[Batch 35 writer](../../tools/windows_preflight_validation.py):

```text
STARTED.json
pytest/console.log
pytest/results.xml
pytest/process-temp/               # optional; contents not enumerated
pytest/temporary-root/             # optional; contents not enumerated
fixtures/missing/manifest.json
fixtures/lexical_refusal/manifest.json
fixtures/normal_path/manifest.json
fixtures/normal_path/ordinary path/example.txt
fixtures/malformed_receipt/manifest.json
fixtures/malformed_receipt/receipt.json
assessments/<case>/first.json
assessments/<case>/second.json
assessments/<case>/summary.txt
result.json
summary.txt
SHA256SUMS
COMPLETE.json
FAILED.json                       # optional; always overrides completion
```

The four mandatory assessment cases are `missing`, `lexical_refusal`,
`normal_path` and `malformed_receipt`. The only optional additional assessment is
`supplied`, with the same three assessment members. Failed/interrupted archives
may contain only part of this structure; they cannot obtain a complete-workflow
result. Unexpected files, unsupported directories, ambiguous names and unsupported
layouts are refused. The excluded temporary-directory roots must themselves pass
ordinary-directory/link checks, but their contents are never enumerated or read.

Supplied input originals are not copied by the writer. Their absence from the
archive is expected. The verifier can compare recorded input identities with
recorded assessment identities, but cannot independently verify absent supplied
bytes or historical input immutability. Those evidence states remain
`not_assessed`.

## Checksums and consistency checks

`SHA256SUMS` uses the writer's sorted lowercase SHA-256, two-space separator,
relative-path format. The verifier rejects duplicate and case-ambiguous entries,
unsafe paths, unsupported members, missing listed files, incorrect hashes and
incomplete coverage of supported evidence files. Every declared digest is checked
against the bounded bytes actually read.

The writer intentionally excludes `SHA256SUMS`, `COMPLETE.json` and any later
`FAILED.json` from its listed-file inventory. `COMPLETE.json` separately references
the exact result and inventory digests. The verifier checks those references and
the markers' schemas/security flags; no self-referential digest is invented.
Temporary-tree contents are explicitly outside checksum coverage. Thus
`verified` never means that every byte below the archive directory was inventoried.

Additional checks include:

- Agreement between start/result source revision, baseline, host and timestamps;
  source-pin and harness-fingerprint structure. These are recorded claims, not
  independently authenticated Git or host facts.
- The fixed 162-case JUnit selection, unique case identities, declared suite counts,
  actual pass/fail/error/skip outcomes and the required NTFS case; matching result
  accounting and completion status. Valid JUnit observations can remain visible
  even if completion or checksum verification fails.
- Equal repeated assessment reports, valid five-state accounting, unchanged-input
  declarations, matching summaries and recorded inventory/report identities.
- The writer's exact four inert fixture definitions and their retained byte
  identities. A coherent replacement experiment is not accepted as a known fixture.
- Explicit nonqualification flags, supported evidence classifications and consistent
  host declarations. No result can grant execution, signing or production approval.

`FAILED.json` takes precedence even when a valid-looking `COMPLETE.json` and
matching checksums exist. A malformed failure marker also prevents success. A
late writer persistence/cleanup failure can leave both markers; never remove the
failure marker or recreate evidence to obtain a passing classification.
If an unsafe layout stops inspection before marker assessment, workflow remains
`not_assessed` with blocked integrity; a failure is not silently accepted as
completion. The tool does not open unsafe paths simply to discover a marker.

## Report interpretation and exit codes

Integrity and workflow are separate dimensions. The verifier may report internally
consistent listed evidence alongside a failed workflow, or preserve recorded test
outcomes alongside invalid/incomplete integrity.

| Integrity state | Meaning |
|---|---|
| `verified` | Supported completion records and their listed-file integrity/consistency checks agree. This is not authenticity. |
| `missing` | The selected archive/member or required sealing/completion evidence is absent or incomplete. |
| `mismatch` | Declared hashes, schemas, metadata, counts, fixture definitions or relationships disagree. |
| `blocked` | A path, type, size, resource, malformed-input or observable-capture boundary prevents assessment. |

Workflow values are `not_assessed`, `incomplete`, `failed`, `completed`, and
`completed_with_unverified_cases`. Missing evidence does not become a pass. Skips
remain explicit unverified cases. The report's independent native execution,
supplied-original verification, historical immutability, signature trust and source
authenticity fields remain `not_assessed`; `native_windows_verified`,
`runtime_qualified` and `concurrent_path_isolation` remain false.

| Exit code | Meaning |
|---|---|
| `0` | Declared integrity is consistent and the workflow is completed without skipped cases. |
| `1` | Failed, incomplete, missing or completed-with-unverified-cases evidence; review both dimensions. |
| `2` | Integrity mismatch, blocked assessment or invalid command arguments. |

KeyboardInterrupt, SystemExit and other control-flow exceptions propagate normally;
they are not converted into a normal verification result. Do not interpret an
interrupted command's absent/truncated standard output as completed evidence.

The accepted `native_functional_preflight` class denotes a claim stored by the
writer. Mutually agreeing host/class metadata cannot establish that execution
actually occurred on Windows; synthetic fixtures can reproduce those strings.
The supported `portable_synthetic_validation` class additionally requires the
recorded limitations `native_windows_verified=false`, `checkout_verified=false`
and `working_tree_dirty=true`, together with consistent non-Windows host metadata.
Neither class authenticates its creator.

## Security review and resource boundaries

Static checks reject unsafe lexical spellings, traversal, protected/original
checkout destinations, symlinks, reparse points, hard-linked regular files,
special files and unsafe parents before supported member reads. Paths are
whitelisted before directory descent. Unknown names and raw parser/OS errors are
not echoed in public reports. Private logs and JUnit text are read for integrity
but are not copied into the JSON or human summary.

| Bound | Limit |
|---|---|
| Assessed files | 128 |
| Enumerated supported entries | 256; excluded temporary contents are not enumerated |
| Ordinary archive member | 16 MiB |
| Aggregate retained member bytes | 32 MiB, with separately bounded consistency rereads |
| JSON, XML or checksum record | 1 MiB |
| JSON structure | Depth 12; 8,192 nodes; duplicate keys/nonfinite values rejected |
| XML structure | Depth 16; 4,096 elements; 32 attributes per element; UTF-8 without NUL, DTD or entity declarations |

Recorded external input sizes use the writer's input-specific limits, rather than
the archive's member limit: runtime/companion records may describe up to 64 MiB,
while manifests and receipts are limited to 1 MiB. No external file is read to
confirm those historical records. Bounded parsers/readers limit work but do not
provide a separately enforced OS memory/time quota or a sandbox.

Review identified and addressed internal consistency hazards: applying the archive
size cap to external inventory metadata; accepting stale report identities after
fixture/inventory edits; accepting changed fixture semantics; incomplete report
schema/state validation; bool/integer accounting aliases; nonfinite decimal
overflow; and losing JUnit observations merely because a workflow failed.
The [synthetic regressions](../../tests/product/test_windows_preflight_archive.py)
cover these cases together with checksums, completion/failure precedence, links,
resource limits, deterministic output, sanitization and control-flow propagation.

Observable file-byte, identity and directory-entry changes during capture are
rejected using the shared bounded reader and final consistency checks. **These
checks are not an atomic snapshot.** Preserve the unresolved **MEDIUM**
[Batch 34 B34-03 hostile-parent-replacement limitation](batch34-preflight-security-review.md):
a hostile concurrent parent replacement can redirect a read before rejection.
Stable developer-controlled inputs are a precondition, not independently enforced
access isolation. Do not use this tool as a hostile-filesystem security boundary.

Checksums can detect disagreement with declared bytes, not prove when, where or by
whom they were created. An attacker who rewrites a self-consistent archive can
rewrite its checksums too. There is no detached signature, publisher trust,
original Windows attestation, firmware-execution proof or runtime approval.
